# 极端情况恢复加固

日期：2026-09-26。延续低性能设备与卡顿恢复优化。此次只修改媒体生命周期、异常回滚与重连等待，没有增加生产依赖、服务端媒体处理或信令协议。

## 发现与修复

| 极端情况 | 原问题 | 当前处理 |
| --- | --- | --- |
| 重连未完成，连接先恢复又再次中断 | 旧异步请求完成后覆盖新恢复周期的计时器 | 每轮重试检查自身身份；旧周期不能安排后续重试，每轮独立防并发 |
| 网络恢复通知连续触发 | 需要确保通知不会重复协商或延长截止时间 | 保持最多 3 次尝试与原截止时间；20 次通知注入只产生 1 个正在等待的协商 |
| 网页摄像头或屏幕在接入 sender 时结束 | 结束事件发生在监听安装之前，UI 错误显示开启 | 异步接入前后检查轨道与流生命周期，清理失效媒体；共享撤销服务端占用 |
| 网页共享接入过程中挂断 | 接入完成后仍可能创建音频节点 | 返回后先检查会话和捕获流身份，不再创建节点或显示共享 |
| 自动降档失败，回滚也失败 | 忽略回滚失败，逻辑档位与设备实际状态可能不一致 | 停止受影响摄像头或屏幕共享，保留房间、语音与另一条媒体；网页和 Android 摄像头显示重开提示，Android 共享回到停止状态 |
| Android SDP 协商回调一直不返回 | 重连协程卡在 offer，后面的截止时间检查无法执行 | 用剩余的 30 秒预算约束整个协程等待；网络切换继续使用原预算 |

降档失败但回滚成功时仍保留此前的 15 秒冷却策略。不会把一次可恢复的参数拒绝当作必须停止视频的故障。用户画质目标和锁定不变。

## 实际验证

先运行新增测试复现旧代码问题：旧重连覆盖新计时器、摄像头/屏幕已结束却标记开启、回滚失败却继续保持媒体开启。修复后通过。

- 网页全部 **37 项**测试通过，本轮增加 **7 项**，使用可控 Promise、轨道状态、参数异常和虚拟计时器覆盖上述生命周期与重连边界。
- Android 原有 **18 项**单元测试通过；Debug、Release 构建成功。
- Debug lint：**0 错误、8 条既有警告**；Release vital lint 通过。
- `git diff --check` 通过；CodeGraph 索引已更新。

本轮测试验证的是异常控制流，不是新的帧率或端到端恢复时间测量。Android 永不返回的 SDP 回调路径经过代码追踪和编译检查，未在实体设备上注入该驱动故障。上一轮真实 Chrome 媒体链路与模拟器断网记录仍见《低性能设备与卡顿恢复验证》，不将其冒充本轮新测试。

30 秒是可调度环境下的恢复预算，不保证操作系统冻结、主线程完全阻塞或应用被杀时准时执行。实体低端机的持续温控降频、硬件编码器故障、接收端性能瓶颈和极低网络带宽仍需设备实测；不能承诺这些条件下同时保持高分辨率、高帧率和零卡顿。

本轮没有启动浏览器、模拟器、服务或容器，无新增测试运行资源需保留。
