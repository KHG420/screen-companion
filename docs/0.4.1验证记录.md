# 0.4.1 录屏切换性能修复

修复 Android 录屏在显示通知、重复应用画质设置时不必要地重设采集表面的问题。只监听默认屏幕；仅实际尺寸变化才调用 WebRTC 的 `changeCaptureFormat`，仅尺寸或帧率变化才更新源适配器。停止共享时清除缓存，参数应用失败时允许回退重新应用。

## 原因与范围

检查项目实际使用的 WebRTC 144.7559.15 字节码：`ScreenCapturerAndroid.changeCaptureFormat` 即使尺寸相同也同步等待采集线程，更新纹理尺寸并重设虚拟显示的表面。因此重复调用会增加切换期间的采集开销。保持原有清晰度、码率和帧率目标，不改变网络协议、语音混音或视频轨道。

## 对照验证

两台 Android 35 模拟器建立真实 WebRTC 通话。旧版加入临时调用日志，新版记录实际尺寸重设。相同操作：重复应用当前画质 3 次、设置应用与同屏之间切换 3 轮、横屏后恢复竖屏。

| 采集表面重设 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 重复应用相同画质 | 3 | 0 |
| 横屏后恢复竖屏 | 6 | 2 |
| 切换应用 | 0 | 0 |
| 总计 | 9 | 2 |

接收端仍显示共享状态并持续解码画面。旧测试脚本使用已过时的“全屏观看”文本导致末尾断言失败；检查实际 UI 与解码计数后改为当前的“对方正在共享”，不将这个脚本问题当作产品故障。

这证明减少了冗余表面重设，不代表帧率提高 78%，也不代表解决所有设备、网络或摄像头切换卡顿。模拟器不能替代真机硬件编码性能验证。

补充验证：30 → 60 → 30 FPS（同时调整码率和资源优先级）未重设采集表面；停止并重新共享后再旋转两次，恰好重设两次。接收端解码帧数继续增加，并检查了接收画面的截图。
