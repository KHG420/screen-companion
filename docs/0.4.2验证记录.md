# 0.4.2 动态画面性能验证

## 实现

- Android 屏幕源根据已有优先策略使用动态内容或屏幕细节编码；网页同样只对“清晰优先”设置 detail 提示。WebRTC 的 screencast + BALANCED 会退化为保分辨率策略，导致动态内容在负载高时持续掉帧。动态内容路径允许既有均衡策略生效，同时保留显式清晰优先。
- 网页只有宽、高或帧率的采集约束实际变化时才重新应用；码率和优先策略单独更新。Android 重复应用同一个 Quality 直接返回，继承 0.4.1 的表面尺寸去重。
- 两端显示按统计周期增量计算的编码/帧、发送排队/包、解码/帧、接收缓冲/帧耗时与本周期冻结次数。发送排队按包取平均，不能和每帧指标直接相加当作端到端延迟。网页一次统计只触发一次界面更新。
- Release 启用 R8 优化和资源压缩；签名独立配置，不在仓库保存签名密钥或测试服务地址。

## 动态输入对照

两台 Android 35 ARM64 模拟器，软件 GPU；共享方展示持续移动的条纹、文字、色块和帧计数器。均衡目标 1080p / 30 FPS / 8 Mbps，约 35 秒。以 WebRTC 周期累计值作差，忽略第一段热身。原始日志保存在本地忽略目录 `.tools/deep-baseline-emulator-*.txt` 与 `.tools/deep-fixed-emulator-*.txt`。

| 指标 | 0.4.1 内容路径 | 新内容路径 |
| --- | ---: | ---: |
| 发送 FPS | 13.75 | 17.91 |
| 接收 FPS | 13.99 | 18.28 |
| 编码平均 ms/帧 | 50.39 | 24.80 |
| 发送排队平均 ms/包 | 82.57 | 6.51 |
| 解码平均 ms/帧 | 14.19 | 9.04 |
| 接收缓冲平均 ms/帧 | 150.54 | 111.87 |
| 测试窗口累计冻结次数 | 4 | 1 |
| 测试窗口累计冻结秒数 | 1.493 | 0.534 |

两次末尾发送尺寸均为 1080×1920。编码器为 libvpx，接收解码器为 c2.goldfish.vp8.decoder。测试不是严格隔离的统计基准；主机负载、软件模拟器和短窗口都会影响数字。不能将结果外推为所有真机的固定提升比例或宣称达到 30/60 FPS。

## 桌面浏览器

复用现有 Chrome，使用 `web/tests/performance.html` 生成 1080p/30 FPS 滚动文字与色块，经实际 Call 和 WebRTC 传送，热身 5 秒后取 15 秒增量。VP8 默认路径约 29 FPS，无冻结；H.264 对照没有稳定显示更高 FPS，因此保留现有协商，不强制换编码器。该测试不代替操作系统录屏权限及真实网络验证。

## 回归范围

- Web 单元测试 10 项，包含采集约束去重、内容提示、参数失败回退、统计增量与重置处理。
- 浏览器实际 WebRTC 回归：双向文字、摄像头与屏幕并行、屏幕交接、4K 独立参数和关闭清理。
- Android Debug/Release 编译、单元测试、两种构建的 lint；优化后的 APK 已在两台模拟器覆盖安装，通过 HTTPS 建房、录屏、动态画面接收、4K/流畅/均衡切换、摄像头与共享并行、前后摄像头切换及文字发送检查。

参数仍为目标上限，保留 4K、1–60 FPS、0.5–80 Mbps 和清晰优先。未新增生产依赖、信令字段或服务器媒体转发层。

## 优化构建验收

首次 R8 安装验证发现 SDK 未附带 consumer ProGuard 规则，原生库加载时找不到 `org.jni_zero.JniInit`。已仅保留 org.webrtc 与 org.jni_zero 的 JNI 边界，其他应用代码与资源继续优化。修正后重新构建、安装并完成上述通话检查；不是仅编译通过。

最终安装包为 51,318,785 字节（约 48.94 MiB），versionCode 7 / versionName 0.4.2；不可调试、只允许 HTTPS，沿用先前本地测试签名，可覆盖安装。此签名仍只适用于测试分发。SHA-256：`bac7664f31666c1f47d718dd0013103ea505ad5ad2ed413651fe9a5583b3ff20`。

网页生产文件仅更新 call.js，已从线上重新读取并逐字节核对。公开源码和安装包不包含测试服务配置。
