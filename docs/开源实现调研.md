# 安卓屏幕共享与语音聊天：开源实现调研

调研日期：2026-09-24。目标：两台安卓手机，一路屏幕共享、双向语音，高画质、低延迟。

## 1. ScreenStream：最接近安卓共享屏幕的参考

仓库：https://github.com/dkrivoruchko/ScreenStream

使用 MediaProjection，包含独立的 MJPEG、WebRTC 和 RTSP 模块。WebRTC 模式支持屏幕、麦克风及内部音频，使用 stream ID 与密码连接。README 链接的配套信令服务与网页客户端：https://github.com/dkrivoruchko/ScreenStreamWeb （此次未深入审核服务端实现）。

核对到的实现：

- WebRtcProjection.kt：配置 EGL、WebRTC 编解码工厂、音频设备模块，并参考设备硬件编码支持调整编码器偏好。
- WebRtcClient.kt：创建视频和音频发送轨道；OfferToReceiveVideo 与 OfferToReceiveAudio 均为 false，当前流程是广播观看，不能视为双向通话成品。
- WebRtcClient.kt：通过连接尝试标识避免陈旧协商回调污染当前会话，管理尚未应用远端描述时的候选信息；值得借鉴。
- ScreenCapturerAndroid.kt：管理 VirtualDisplay 和采集尺寸调整。
- 当前客户端设置 BALANCED 降级偏好，仍有码率设置 TODO，不能把默认配置当成已经针对本产品优化的结果。

代码入口：https://github.com/dkrivoruchko/ScreenStream/tree/924336b3ac8be6813243c872849411e04e69027b/webrtc/src/main/java/info/dvkr/screenstream/webrtc/internal

适合借鉴采集生命周期、硬件编码选择、信令状态管理和简单连接体验。不能直接照搬 MJPEG 模式作为高清实时通话通道。官方不同发行渠道包含的模块不同，需注意 F-Droid 版本不含 WebRTC。

## 2. LiveKit：最值得参考的通话 SDK

Android：https://github.com/livekit/client-sdk-android
服务端：https://github.com/livekit/livekit

核对到的实现：

- LocalScreencastVideoTrack.kt：按显示尺寸及方向调整采集，关联前台服务，并在共享停止时清理服务和方向监听。
- LocalParticipant.kt：屏幕共享与摄像头使用独立默认参数；当前源码对屏幕共享使用 MAINTAIN_RESOLUTION，对摄像头使用 MAINTAIN_FRAMERATE。这支持把“文字清晰”与“运动流畅”做成不同策略。
- RTCEngine.kt：包含连接恢复及重连策略，适合参考通话状态生命周期。
- AudioSwitchHandler.kt：音频设备切换和音频焦点处理，底层使用 AudioSwitch。
- README 明确默认音频模式面向双向通信。

代码入口：https://github.com/livekit/client-sdk-android/tree/8875d695e59e03721b08cbc190a2681ce643d857/livekit-android-sdk/src/main/java/io/livekit/android

LiveKit 服务端明确是 SFU。采用它作为完整底座意味着媒体经 LiveKit 服务端转发，不能同时宣称是手机间原生 P2P 直连方案。可自建，不必须使用付费云；但仍要承担媒体服务器出口流量。SFU 的常规传输加密也不等于默认启用客户端间端到端加密。

适合以最快速度搭建可用通话原型；若坚持一对一直连优先，可参考其设计而不引入整个 SDK。两条路线都需要实际设备与目标网络验证。

## 3. scrcpy：低延迟显示与编码的参考

仓库：https://github.com/Genymobile/scrcpy

官方 README 宣传 35–70 ms 低延迟，但这是 scrcpy 的使用场景数据，不能用作跨公网手机通话承诺。

核对到的实现：

- doc/develop.md 与 doc/video.md：默认不增加视频播放缓冲，尽快解码显示；音频使用适当缓冲。
- SurfaceEncoder.java：使用 MediaCodec Surface 输入，设置实时优先级与低延迟相关参数；初始编码失败时支持尝试更小尺寸。
- app/src/frame_buffer.c：管理待显示帧，适合研究如何避免显示端积压。
- 音频、视频和控制分离处理。

文档：https://github.com/Genymobile/scrcpy/blob/19c1261d2e2cbf2b5e6a71a8b64cc1dd3ede06ac/doc/develop.md
编码：https://github.com/Genymobile/scrcpy/blob/19c1261d2e2cbf2b5e6a71a8b64cc1dd3ede06ac/server/src/main/java/com/genymobile/scrcpy/video/SurfaceEncoder.java

主要场景是电脑通过 USB/TCP-IP 操作安卓，屏幕采集依赖 shell 权限链路。普通手机应用应使用 MediaProjection，不能复制其权限方式。互联网传输仍需要 WebRTC 抖动缓冲和拥塞控制，不能机械照搬“所有缓冲设为零”。也不能在压缩码流中任意丢帧破坏帧间依赖。

## 4. RustDesk：远程协助和连接回退的参考

仓库：https://github.com/rustdesk/rustdesk

README 明确列出 rendezvous 与 relay；src/rendezvous_mediator.rs 管理相关交互。安卓 MainService.kt 包含 MediaProjection、前台服务、编码和采集停止恢复处理。AudioRecordHandle.kt 存在语音通话流程，使用 VOICE_COMMUNICATION，并处理通话与播放采集之间的切换。

代码入口：https://github.com/rustdesk/rustdesk/tree/58ff78a823fe9ec5fe90f6017261c241656014c2/flutter/android/app/src/main/kotlin/com/carriez/flutter_hbb

可参考邀请、接受连接、状态呈现和直接连接失败后的中转逻辑。它使用 Flutter、Rust 和原生安卓组合，整体范围超过本产品需要。AGPL 并非禁止商用，但直接复制/修改/分发及相关网络使用可能触发源码提供义务；闭源产品不能把它当成 MIT/Apache 项目直接复用。架构思路学习和代码整合要分开。

## 5. Jitsi Meet：完整通话产品与 P2P 策略参考

仓库：https://github.com/jitsi/jitsi-meet
配置：https://github.com/jitsi/jitsi-meet/blob/master/config.js

README 提供 Android 客户端入口。config.js 的 p2p 配置明确：两人时尝试直接连接，成功后停止经 JVB 发送媒体；第三人加入时切回 JVB。也区分移动端编码偏好与屏幕共享编码配置。

可参考成熟会议中的加入、静音和会话状态交互，以及双人优先直连的策略。完整会议产品与部署栈对于轻量一对一应用较重；仅凭总配置不能保证所有安卓组合下 P2P 与屏幕共享都按同样方式运行，仍需具体版本验证。

## 针对本项目的建议

保留原规划的 Kotlin 原生安卓 + WebRTC + 轻量信令 + TURN 中转作为优先候选，不因调研而立刻改成会议系统或增加生产依赖。

1. 从 ScreenStream 借鉴安卓采集、前台服务、编码器探测和协商状态管理。
2. 从 LiveKit 借鉴麦克风/屏幕独立生命周期、音频路由、重连及按画面内容选择降级策略。
3. 从 scrcpy 借鉴缩短采集编码显示链路、避免冗余画面队列，并用真机确认编码器行为。
4. 从 RustDesk/Jitsi 借鉴邀请加入、连接状态，以及直连失败时的明确回退体验。
5. 一对一原型中优先使用单视频层，除非测试证明有需要，不默认增加多层编码和多人 SFU。
6. 摄像头参数不能直接当作屏幕共享参数：文字场景优先清晰，快速滚动场景优先帧率，弱网时先保语音。

备选路线是 LiveKit Android SDK + 自建 LiveKit 服务端，优点是更快获得完整通话能力，代价是媒体路径和带宽成本变化。先做独立技术原型对比，再决定；本次调研没有授权或实施架构迁移。

## 第一轮技术验证

在同一批安卓设备、相同分辨率/帧率及码率约束下，对 WebRTC 直连、强制 TURN、必要时 LiveKit SFU 分别测量。覆盖同 Wi-Fi、跨网络、移动网络、限速丢包、旋转、系统停止采集及 30 分钟持续使用。

统计首帧时间、画面端到端延迟 P50/P95、文字清晰度、语音回声与断续、实际码率、编码耗时、耗电及温度。不能用 RTT 替代端到端延迟，也不能以 Star 数量或源码参数推断谁的实际性能最好。
