# 0.4.4：覆盖其他分辨率与帧率

## 修正范围

- 浏览器不再用固定 3840×2160 / 60 FPS / 40 Mbps 能力探测筛掉普通设备，而是在协商时按当前画质检查 H.264 编码和解码能力。已用“只能高效处理 1080p30”的能力模拟复现旧版漏选并验证修复。
- 能力探测按尺寸、帧率和码率缓存；重新协商时目标改变会重新探测。同次通话内的普通画质调整保留已经协商的编码和轨道，不强行重协商。
- Android 在启动屏幕采集前应用发送码率、帧率和降级策略，避免首帧采用默认发送限制。保持此前仅在尺寸变化时重设虚拟显示的实现，单改帧率由源适配器处理，单改码率不重建采集。
- 保留所有已有预设、自定义 1–60 整数 FPS、0.5–80 Mbps、横竖屏及三种降级策略。没有增加生产依赖或修改信令协议。

## 验证方法与范围

`web/tests/quality-matrix.html` 使用真实 WebRTC 编码/传输/解码，不用目标参数代替输出统计。每个独立用例先按产品默认画质建立连接，再在房间中设置该用例目标。

- 180p、360p、720p、1080p、1440p、2160p，各测 15 / 30 / 60 FPS。
- 1080p 补测 1 / 5 / 10 / 20 / 24 / 25 / 45 FPS，以及均衡、文字清晰、动态流畅预设。
- 720p60 / 0.5 Mbps 分别测自动平衡、保分辨率、保帧率；这是低码率上限测试，不等同真实弱网丢包、抖动或限速测试。
- 另测静止画面；静止内容降帧属于正常节流，不按动态素材帧率判失败。
- 连续切换在同一对端连接、同一源轨道上跨分辨率、帧率和码率运行，检查轨道、发送器和接收轨道身份保持不变，并确认后续持续接收。

动态素材按目标尺寸生成移动文字、条纹与色块。独立用例热身 8 秒后采 3 个 3 秒窗口；每个窗口同时满足实际发送/接收尺寸和发送/解码/呈现 FPS ≥目标的 95%，才标记 nearTarget。该判据只是短时间回归，不代表长期稳定或跨设备保证。呈现取视频回调的累计 presentedFrames 差值，不把 JS 回调次数当作视频帧数；这也不是对物理显示器扫描输出的测量。连续切换用 4 秒热身、2 个 3 秒窗口。

测试复用现有 Chrome 和用户运行环境，同一台 M4 Mac 同时发送与接收。未关闭用户其他应用，没有隔离性能干扰。此测试源替代浏览器录屏授权流程，原生显示器像素、刷新率和系统采集开销仍需实际设备验证。

参数回归在网页和 Android 分别遍历 6 种尺寸 × 60 个整数帧率 × 3 种策略，核对独立参数与编码提示；网页还检查仅改码率不会重新设置采集约束。这是参数覆盖，不代表 1080 个组合都做过真实性能测试。

## 接收缓冲对照

1440p30 交替测试浏览器默认缓冲与 `jitterBufferTarget=0`，每种各两轮。默认两轮平均呈现 29.91 / 29.82 FPS，测量窗口均无呈现丢帧；目标 0 的两轮为 29.75 / 28.16 FPS，第二轮出现 15 帧呈现丢帧。接收缓冲平均值也没有随目标 0 稳定下降。因此没有在产品中添加该设置，继续使用浏览器的自适应缓冲。API 的目标值不能当作实际延迟。

## 连续切换

720p15 → 1080p30 → 1440p60 → 4K30 → 720p60 → 1080p30 → 1080p30/2 Mbps 七步均保持原有源轨道、发送器、接收轨道和连接。参数调用耗时 0.5–4.4 ms，仅代表 API 应用耗时，不是端到端画面切换延迟。部分窗口存在呈现丢帧；不据此宣称完全无卡顿。最后一步的低码率与自动平衡导致实际发送下降到 720p/540p，属于允许的适配，未记为原目标分辨率达标。

## 各档位的实际呈现帧率

以下为保分辨率模式、独立动态素材用例的平均呈现 FPS。各行码率不同；结果不能解读为尺寸越小必然越快。

| 目标尺寸 | 码率上限 | 15 FPS 目标 | 30 FPS 目标 | 60 FPS 目标 |
| --- | ---: | ---: | ---: | ---: |
| 180p | 0.5 Mbps | 15.1 | 30.1 | 33.7 |
| 360p | 1 Mbps | 15.0 | 29.8 | 57.6 |
| 720p | 4 Mbps | 15.0 | 30.0 | 59.3 |
| 1080p | 8 Mbps | 15.1 | 30.0 | 59.0 |
| 1440p | 16 Mbps | 14.9 | 27.2 | 57.2 |
| 2160p | 40 Mbps | 14.8 | 29.5 | 36.5 |

180p60 / 0.5 Mbps 的实际编码耗时只有约 1 ms/帧，但发送帧率约 38 FPS，码率已贴近上限；不能把它归为分辨率太高或 CPU 不足，也不能承诺最低码率满足动态 60 FPS。部分 360p60、1440p 和 4K 档位有呈现丢帧。此表展示平均值，严格逐窗口判据见 JSON。

自动平衡与帧率优先的独立用例中，1080p24、1080p45、均衡和动态流畅预设曾降到 720p；采样统计报告 bandwidth 限制。低码率测试更明显：720p60 / 0.5 Mbps 的保分辨率平均发送约 23 FPS；自动平衡下降到 360p，保帧率下降到 360p/270p 且仍未恒定 60 FPS。策略是取舍偏好，不是硬件或网络无法满足时的保证。

静止素材修正了测试页“只在挂接前提交一次 Canvas 帧”的问题，启动时短暂重复绘制相同像素，再停止提交；最终确认初始画面被解码，热身后的编码和传输帧率为 0，连接保持。早期缺失首帧的测试数据未用于静止节流结论。

完整汇总见 `quality-performance-measurements.json`。低帧率短窗口存在计数边界波动，不能只凭 1 FPS 用例某个 3 秒窗口不足 0.95 FPS 就断言持续掉帧。

## Android 安装包功能验收

两台 Android 35 ARM64 模拟器安装最终 Release 包，验证从 720p15 起播，依次切换 1080p30、1080p60、1440p24、1080p45，再仅将码率从 12 Mbps 改为 3 Mbps。每步都保持通话并收到画面，最终停止共享和挂断通过。发送源为 1080×1920，1440p 目标仍按实际源尺寸发送，未放大。为读出完整统计，接收端测试显示高度临时增大；两端尺寸已恢复。

这些属于安装包和热切换功能验证。模拟器使用软件处理，编码/呈现明显受限，统计窗口也包含切换回应用界面的静止内容；不把其 FPS 当作安卓真机性能基准，更不据此保证真机 60 FPS。
