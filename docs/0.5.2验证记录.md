# 0.5.2：手动画质优先

验证日期：2026-09-26。范围为安卓与电脑端精确设置对自动降级策略的优先级；没有新增生产依赖，也没有修改信令协议、服务端接口或持久化数据。

## 原因与实现

旧实现只记录自动策略，手动填写尺寸或帧率后仍把原来的策略交给编码器。例如“动态流畅”之后手动选 4K，原来的保持帧率策略依然允许降低分辨率。

本次在通话内独立记录分辨率、帧率是否锁定。手动输入与快捷选择都会锁定对应项；改变码率不解除锁定。优先级如下：

| 锁定状态 | 编码器策略 |
| --- | --- |
| 只锁定分辨率 | 保持分辨率，允许降帧 |
| 只锁定帧率 | 保持帧率，允许降分辨率 |
| 两项都锁定 | maintain-framerate-and-resolution，不主动调整这两项 |
| 两项都未锁定 | 使用用户选择的自动策略 |

存在锁定时，自动策略选项禁用，并解释如何取消锁定。主动重选预设会重新填写参数与锁定状态。安卓与电脑默认锁定分辨率。界面显示实际发送/接收数据；锁定项目未达标时显示提示。参数仍为目标，码率仍是上限，拥塞控制保留，不放大低分辨率源。

安卓设置后读取原生 sender 参数确认接受；网页也读取 sender 参数确认。浏览器拒绝或忽略锁定策略时，当前设置操作报错并尝试恢复原设置，恢复失败则停止共享；不悄悄退回另一种策略。

## 验证

- 14 项安卓单元测试通过，包括手动锁定覆盖所有自动策略、修改码率保持锁定、横竖屏尺寸计算及独立帧率组合。
- 21 项网页测试通过，包括实际画质表单事件处理、动态预设后手动选择尺寸、双锁定、修改码率保留锁定、主动重选预设、浏览器拒绝/忽略锁定后的回滚。
- 两台 Android 35 ARM64 模拟器通过实际 WebRTC 通话验证。先选择“动态流畅”，再手动选 720p：原生参数返回 MAINTAIN_RESOLUTION，接收为按源比例计算的 576×1280。
- 再手动选择 30 FPS：原生参数返回 MAINTAIN_FRAMERATE_AND_RESOLUTION，接收仍为 576×1280；该动态素材采样窗口为 24 FPS，不能据此承诺满帧。
- 将码率上限调整为 0.5 Mbps，原生双锁定不变，发送/接收尺寸仍为 576×1280。实际帧率明显不足，发送端显示未达锁定目标提示，而非改写目标值。该低码率检查验证锁定与提示，不代表画质无损或帧率保证。
- 主动重选“动态流畅”后，两项锁定均解除，原生策略恢复 MAINTAIN_FRAMERATE。
- 最终 Release APK 安装到两台模拟器，安装文件 SHA-256 与交付包相同；重新入房、共享、从动态预设手动选择 720p/30 FPS 后，界面显示双锁定，实际发送与接收为 576×1280。对锁定控件、禁用自动策略和未达标提示完成截图检查。
- Debug、Release 构建及 lint 通过。lint 无错误，Debug/Release 分别保留 8/9 条既有警告，涉及依赖版本、PiP、备份、资源版本、Kotlin 扩展与单色图标。
- 电脑浏览器自动化连接返回 request-header policy 不可用，因此没有本轮浏览器交互或真实浏览器媒体验收；未另启隔离浏览器。网页表单事件、编码参数和错误恢复由 Node 回归测试覆盖。
