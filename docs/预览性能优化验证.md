# 预览播放与后台渲染优化

日期：2026-09-26。此次优化减少不可见视频的本地播放和渲染工作；不增加服务端处理、生产依赖或协议消息，不改发送清晰度与用户画质锁定。

## 实现

网页原先只用 hidden 隐藏摄像头容器，视频仍播放。现在收起摄像头时暂停对应 video 元素，重新显示后复用原轨道恢复播放。页面进入后台时暂停本地视频播放，屏幕画中画除外；回到前台后自动恢复。音频播放与媒体发送不受这段逻辑控制，没有停止或禁用采集轨道。

Android 原先只在 Compose 组件销毁时解绑 VideoTrack 的渲染 sink。现在按 Activity 生命周期绑定：STARTED 及以上保持渲染（包括画中画的暂停但仍可见状态），STOPPED 时解绑，重新可见时绑定。不关闭发送端摄像头或共享。处理了后台通话已结束、前台状态尚未重新收集时旧轨道已释放的情况。

## 浏览器前后测量

复用原有 Chrome，使用 `web/tests/preview.html` 加载实际 app.js 与 index.html，以 1280×720 / 30 FPS 动态 canvas 流驱动摄像头及共享预览。每个阶段预热后，记录 2 秒内本地摄像头 video 的 getVideoPlaybackQuality().totalVideoFrames 增量。

| 阶段 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 显示摄像头预览 | 60 帧 | 59 帧 |
| 收起摄像头预览 | 61 帧、仍播放 | 0 帧、已暂停 |
| 再次显示 | 61 帧 | 60 帧 |

全过程轨道 readyState=live、enabled=true，共享预览没有暂停。原始记录见 [preview-measurements.json](preview-measurements.json)。这证明隐藏预览的播放帧工作已消除；没有测量 CPU 百分比、功耗或端到端通话帧率，不能据此宣称相同幅度的整机性能提升。网页暂停显示不保证停止 WebRTC 接收解码，网络接收仍由浏览器负责。

测试中发现浏览器缓存了旧 app.js，随后测试夹具明确使用 no-store，并确认实际加载新函数后重新测量；表格“修改后”取最终新代码结果。
