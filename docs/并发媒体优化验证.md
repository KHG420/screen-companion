# 摄像头与屏幕共享并发优化

验证日期：2026-09-26。基于 0.5.2；保留版本号和用户画质设置语义。本次修改客户端媒体参数与统计，不改变服务端接口、信令协议、数据格式或生产依赖。

## 定位与实现

原来屏幕通道有硬件 H.264 优先逻辑，摄像头通道没有。旧版浏览器并发基线实际协商为屏幕 H.264、摄像头 VP8。摄像头只设置码率与帧率上限，没有明确降级偏好，且在轨道接入或开始采集后才设置上限。连接详情只展示屏幕，纯视频通话无法通过界面诊断帧率和缓冲。

- 浏览器摄像头按自身的 1280×720 / 30 FPS / 2 Mbps 目标检查编码和解码能力，复用已有 H.264 优选逻辑，不受屏幕 4K 能力探测影响。保留全部其他编码供协商回退。能力探测结果按目标缓存。
- Android 摄像头也使用现有硬件编码探测与 H.264 优选；无对应硬件编码时继续使用原生默认顺序。
- 摄像头使用 motion 提示（网页）和 maintain-framerate 降级策略（两端），在编码或带宽不足时允许降低摄像头分辨率。共享的分辨率、帧率锁定继续有效。
- 摄像头相对码率分配权重设为默认屏幕的 0.5：网页 priority=very-low，Android bitratePriority=0.5。它是本地发送器之间的分配权重，不是固定减半码率；单独视频通话仍可使用原来的 2 Mbps 上限。未设置额外最低码率，不绕过 WebRTC 拥塞控制。
- 摄像头的编码限制先应用，再接入首帧；挂断发生在参数设置等待期间时，网页停止晚到的媒体，不重新附加轨道。
- 连接详情分别展示摄像头和屏幕的实际发送/接收尺寸、区间帧率、码率和编码/解码/缓冲数据。摄像头统计不会错误触发屏幕锁定告警。

架构继续为 WebRTC 直连优先，TURN 作为必要中转；Go 服务只处理信令。没有服务端解码、混流、转码或新增 SFU。中转带宽随实际发送量变化，不能据单机结果推算公网服务器容量。

## 浏览器实测

使用用户已有 Chrome，同一测试页运行两个实际 Call 实例，通过本地 Go 信令和 TURN 建连。输入为合成动态 Canvas，不访问真实摄像头或真实屏幕。屏幕目标 2560×1440 / 30 FPS，双向摄像头目标 1280×720 / 30 FPS。预热 15 秒后取 5 个各 3 秒的窗口。测试时保留用户其他应用，宿主机还运行 Android 模拟器；结果不是独占机器或真实公网的标准化基准。

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 屏幕编码 | H.264 | H.264 |
| 摄像头编码 | VP8 | H.264 |
| 屏幕发送尺寸 | 全部 2560×1440 | 全部 2560×1440 |
| 摄像头尺寸 | 出现 960×540、1280×720 | 两路全部 1280×720 |
| 屏幕发送帧率均值 | 29.70 FPS | 29.70 FPS |
| 共享方摄像头发送帧率均值 | 29.97 FPS | 29.97 FPS |
| 对方摄像头发送帧率均值 | 29.97 FPS | 30.04 FPS |
| 两路摄像头发送码率均值 | 0.64 / 0.89 Mbps | 约 0.10 / 0.10 Mbps |
| 屏幕发送排队均值（每包） | 6.17 ms | 3.96 ms |
| 三路接收的采样期冻结次数 | 0 | 0 |

这说明该输入下同时保持了共享和摄像头的尺寸与帧率，并降低了摄像头流量及发送排队。**不能推导为任意画面的码率节省比例、画质无损或所有延迟指标改善。** H.264 摄像头的编码耗时反而从约 2.5–2.7 ms/帧升至 5.5–5.8 ms/帧；屏幕接收缓冲均值从约 144 ms 变为 165 ms。编码耗时包含实现调度，不能等同 CPU 占用；本次没有测出 CPU 节省比例，也未测端到端显示延迟或主观画质分数。

原始采样见 [concurrent-media-measurements.json](concurrent-media-measurements.json)。可复跑页面为 `web/tests/concurrent.html`，仍需本地信令和能连通的 ICE 配置。页面关闭通话、停止输入定时器与轨道，并恢复媒体方法；测试页面不应部署到生产目录。

## 回归与构建

- Node 网页测试 25 项通过。新增覆盖摄像头首帧前参数应用、独立 720p 编码能力探测、摄像头统计与屏幕锁定隔离，以及参数等待期间挂断后的资源释放。
- Android 单元测试 14 项通过；Debug 与 Release 构建通过。
- Android lint：0 错误，8 条既有警告；Release vital lint 通过。使用工程已有的本地依赖镜像和 lint 缓存脚本解决本机离线缓存缺失，没有修改生产依赖。
- Go `go test -race ./...` 通过。
- 两台 Android 35 ARM64 模拟器启用 emulated 虚拟摄像头后，验证建房、双向摄像头、共享并发、分别显示摄像头/屏幕统计、停止共享、前后摄像头切换、关闭后重新开启及双方挂断返回首页；未发现 AndroidRuntime 崩溃。模拟器并发采样出现约 8–11 FPS 和冻结，因此只视为功能检查，不能视为 Android 流畅度验收。真机硬件编码、持续温控、移动网络与不同设备组合仍需实测。
